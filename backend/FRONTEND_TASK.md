# ТЗ: Frontend для интернет-магазина

## Контекст

Backend уже готов и работает — REST API на Node.js/Express/PostgreSQL (`http://localhost:3000` в деве). Нужен фронтенд, который полностью покрывает этот API: каталог, корзина, оформление заказа, авторизация с подтверждением email, админка для управления товарами/заказами.

Ниже — точное описание того, что отдаёт и ожидает backend, чтобы фронтенд не гадал по коду.

## Стек

Не зафиксирован жёстко — выбирай сама/сам. Разумные варианты: React (Vite) или Next.js, любой стейт-менеджер по вкусу (Context/Zustand/Redux), react-router или встроенный роутинг Next. Главное — не завязываться на server-side rendering там, где это не нужно для SEO (каталог можно, личный кабинет/корзину — нет смысла).

## Базовый URL и формат ответов

- Base URL: `http://localhost:3000` (порт из `.env` backend'а, см. `PORT`)
- Все тела запросов/ответов — JSON
- Формат ошибки всегда одинаковый:
  ```json
  { "error": { "message": "человекочитаемое сообщение", "code": "MACHINE_CODE" } }
  ```
  Коды ошибок: `VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `EMAIL_TAKEN`, `EMAIL_NOT_VERIFIED`, `INVALID_CODE`, `ALREADY_VERIFIED`, `EMPTY_CART`, `INSUFFICIENT_STOCK`, `INTERNAL_ERROR` и т.д.
- HTTP-статусы: `400` валидация/бизнес-ошибка, `401` не авторизован, `403` нет прав, `404` не найдено, `409` конфликт, `500` внутренняя ошибка.

## Авторизация

JWT в заголовке: `Authorization: Bearer <token>`. Токен живёт 1 день (`JWT_EXPIRES_IN`), после истечения любой защищённый запрос вернёт `401` — фронт должен это ловить глобально (interceptor / wrapper над fetch) и разлогинивать пользователя.

Токен несёт `user_id` и `role` (`customer` | `admin`) — после логина/верификации сохраняй `user.role` из ответа, чтобы показывать/скрывать админские разделы.

### Флоу регистрации — двухшаговый, с кодом подтверждения

Это важно: **регистрация не выдаёт токен сразу**. Нужно 2 экрана.

**Шаг 1 — форма регистрации**
```
POST /auth/register
Body: { "email": "...", "password": "..." }   // password >= 6 символов

201 → { "message": "...", "email": "...", "dev_verification_code": "123456" }
409 → EMAIL_TAKEN, если email уже зарегистрирован
400 → VALIDATION_ERROR
```
`dev_verification_code` — код только в деве (пока реальная отправка почты не подключена backend'ом). В проде этого поля не будет, код придёт по email. Учитывай это в UI, но не завязывайся на него в проде — экран ввода кода нужен в любом случае.

**Шаг 2 — экран «введите код из письма»**
```
POST /auth/verify
Body: { "email": "...", "code": "123456" }   // ровно 6 цифр

200 → { "token": "...", "user": { id, email, role, email_verified, created_at } }
400 → INVALID_CODE (неверный или истёкший код, TTL 10 минут)
400 → ALREADY_VERIFIED
```
После успеха — сохраняешь `token`, пользователь залогинен, редирект на главную/каталог.

**Повторная отправка кода** (кнопка «отправить код ещё раз», если пользователь не получил / код истёк):
```
POST /auth/resend-verification
Body: { "email": "..." }

200 → { "message": "...", "email": "...", "dev_verification_code": "..." }
404 → аккаунт не найден
400 → ALREADY_VERIFIED
```

### Логин
```
POST /auth/login
Body: { "email": "...", "password": "..." }

200 → { "token": "...", "user": {...} }
401 → INVALID_CREDENTIALS (неверный email/пароль)
403 → EMAIL_NOT_VERIFIED — если аккаунт не прошёл верификацию
```
Если пришёл `403 EMAIL_NOT_VERIFIED` — не показывай общую ошибку «неверный пароль», а веди пользователя на экран ввода кода (можно сразу дёрнуть `resend-verification`, чтобы код точно был свежим).

## Каталог

### Список товаров
```
GET /products?category=<id>&search=<строка>&page=<n>&limit=<n>&sort=price_asc|price_desc

200 → {
  "data": [ { id, name, description, price, stock_quantity, category_id, image_url, created_at }, ... ],
  "pagination": { page, limit, total, totalPages }
}
```
Все query-параметры опциональны. `search` ищет по подстроке в названии (ILIKE). Товары с `stock_quantity: 0` — показывать как «нет в наличии», не скрывать из каталога.

### Карточка товара
```
GET /products/:id
200 → { id, name, description, price, stock_quantity, category_id, image_url, created_at }
404 → товар не найден
```

### Категории (для фильтра/меню)
```
GET /categories
200 → [ { id, name }, ... ]
```

## Корзина (только авторизованный `customer`)

Все запросы требуют `Authorization: Bearer <token>`. Если роль `admin` — backend вернёт `403`, у админа нет корзины по дизайну.

```
GET /cart
200 → { id, items: [ { id, product_id, quantity, name, price, stock_quantity, image_url }, ... ] }
```
```
POST /cart/items
Body: { "product_id": 1, "quantity": 2 }
201 → { id, cart_id, product_id, quantity }
```
Повторное добавление того же `product_id` **суммирует** количество, а не создаёт вторую строку.
```
PUT /cart/items/:id       // :id — id строки корзины (cart item id, НЕ product_id)
Body: { "quantity": 3 }
200 → обновлённая позиция
```
```
DELETE /cart/items/:id
204 → без тела
```
Фронту нужно самому проверять `quantity` против `stock_quantity` из ответа `GET /cart` для UX-подсказок («в наличии всего 3»), backend это не валидирует при добавлении в корзину — жёсткая проверка остатка происходит только при оформлении заказа.

## Заказы

Требуют авторизации (любая роль).

### Оформление заказа
```
POST /orders   // без тела — берёт текущую корзину пользователя
201 → { id, user_id, status: "pending", total, created_at, items: [ { id, product_id, quantity, price_at_purchase, name }, ... ] }
400 → EMPTY_CART — корзина пуста
400 → INSUFFICIENT_STOCK — сообщение прямо называет товар и сколько доступно, например:
  { "error": { "message": "Not enough stock for \"Deluxe Blender\": requested 3, available 1", "code": "INSUFFICIENT_STOCK" } }
```
После успешного заказа корзина на бэке уже очищена — обнови состояние корзины на фронте (не дёргай `DELETE` вручную).

### Мои заказы / все заказы (admin)
```
GET /orders?status=<status>&user_id=<id>&page=&limit=
```
- `customer` видит только свои — `user_id` в query игнорируется backend'ом.
- `admin` видит все, может фильтровать по `status` и `user_id`.
```
200 → { "data": [ { id, user_id, status, total, created_at }, ... ], "pagination": {...} }
```

### Детали заказа
```
GET /orders/:id
200 → { id, user_id, status, total, created_at, items: [...] }
403 → если это чужой заказ, а пользователь не admin
404 → не найден
```

### Смена статуса (только admin)
```
PATCH /orders/:id/status
Body: { "status": "pending" | "paid" | "shipped" | "delivered" | "cancelled" }
200 → обновлённый заказ
404 → не найден
```

## Админка

Доступ — только пользователи с `role: "admin"` (в сиде: `admin@shop.test` / `admin123`). На фронте роут-гард по `user.role`, но помни, что реальная защита всё равно на backend — фронтовая проверка только для UX.

Нужны экраны:
- **Товары**: список (переиспользовать каталожный список), создание/редактирование (форма: name, description, price, stock_quantity, category_id, image_url), удаление с подтверждением.
  - `POST /products`, `PUT /products/:id`, `DELETE /products/:id`
- **Категории**: список + создание. `POST /categories` (`{ name }`), `409` если имя уже занято.
- **Заказы**: список всех заказов с фильтром по статусу/пользователю, смена статуса через `PATCH /orders/:id/status`.

## Обработка ошибок и edge cases — обязательно на фронте

- Глобальный перехват `401` → сброс токена, редирект на логин.
- `403 EMAIL_NOT_VERIFIED` на логине → редирект на экран ввода кода, а не просто «ошибка».
- `403 FORBIDDEN` на попытке зайти в чужой заказ/админку → сообщение «нет доступа», не крашить приложение.
- `409 EMAIL_TAKEN` на регистрации → подсказать «уже есть аккаунт? войти».
- `400 INSUFFICIENT_STOCK` на оформлении заказа → показать конкретный товар из сообщения, предложить поправить количество в корзине, не терять остальное содержимое корзины (она не откатывается, просто заказ не создался).
- Товар с `stock_quantity: 0` — блокировать кнопку «добавить в корзину» / «оформить», а не полагаться только на серверную ошибку.
- Пустая корзина → скрывать/дизейблить кнопку оформления заказа заранее.
- Пагинация `/products` и `/orders` — использовать `pagination.totalPages`, не считать самостоятельно.

## Критерии готовности

- [ ] Регистрация — двухшаговая (email/пароль → код подтверждения), без прыжка мимо шага верификации
- [ ] Логин корректно обрабатывает `401` и `403 EMAIL_NOT_VERIFIED` по-разному
- [ ] Каталог: фильтр по категории, поиск, пагинация, сортировка по цене — всё через query-параметры `/products`
- [ ] Товар с нулевым остатком визуально помечен и недоступен к покупке
- [ ] Корзина: добавление/изменение количества/удаление, суммирование при повторном добавлении одного товара
- [ ] Оформление заказа обрабатывает `EMPTY_CART` и `INSUFFICIENT_STOCK` с понятным UI, а не общей ошибкой
- [ ] История заказов пользователя + просмотр деталей одного заказа
- [ ] Админка: CRUD товаров, создание категорий, смена статуса заказов — скрыта от `customer`
- [ ] Токен истёк/невалиден → автоматический разлогин, а не зависшее состояние
